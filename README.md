# FormulaSim

A Formula-style single-seater driving simulator for Roblox, written in Luau. It has its own vehicle physics, with no `VehicleSeat` and no Roblox constraints doing the driving. Every force on the car comes from models of the tires, suspension, aerodynamics and powertrain, and is applied with `VectorForce` at the correct world-space points.

This repository is an **exported mirror of the Roblox Studio place** where development happens. It contains every game script plus a [Rojo](https://rojo.space) project file, so the code can be reviewed, diffed or synced back into Studio.

> Status: Milestones A–D done (track, car, input, camera, HUD, suspension, tires, brakes, engine, gearbox, differential, aero). Next up: Milestone E (aero and telemetry tuning) and Milestone F (formal validation suite).

## How it connects to Roblox Studio

Development currently happens **inside Roblox Studio**. Claude Code edits the scripts through the Roblox Studio MCP server, and this repository is exported from the place. Each exported file was checked byte-for-byte against the Studio source (same length and FNV-1a hash).

To load this code into a Studio place yourself, use either option below.

**Option 1: Rojo (recommended)**

1. Install the Rojo CLI and the Rojo Studio plugin (7.x).
2. Run `rojo serve` in the repository root and click **Connect** in the Studio plugin.
3. Rojo writes the scripts into ReplicatedStorage, ServerStorage, ServerScriptService and StarterPlayerScripts. It also sets `Workspace.Gravity = 35.036` (9.81 m/s² at 0.28 m/stud) and `Workspace.StreamingEnabled = false`. Other instances in those services are left alone (`$ignoreUnknownInstances`).
4. Generate the track once from the Studio command bar:
   ```lua
   require(game.ServerStorage.FormulaSim.TestTrackBuilder:Clone()).build()
   ```
5. In the Properties panel, set `Workspace.PhysicsSteppingMethod = Fixed`. Scripts cannot set it.
6. Press Play. Your character is seated in the car automatically.

> Syncing replaces the Studio versions of these scripts with the repository versions. Save your place first.

**Option 2: manual**

Create the same folder and script hierarchy in Studio, using the instance classes listed above, and paste each file's contents in. Then do steps 4–6.

## Physics overview

All simulation maths is done in SI units. `UnitConversion` converts only at the engine boundary.

| Quantity | Conversion |
|---|---|
| Length | 1 stud = 0.28 m |
| Mass | 1 Roblox mass unit = 1000 × 0.28³ = 21.952 kg (density 1 = water) |
| Force | 1 RMU·stud/s² = 6.14656 N |
| Torque | 1 RMU·stud²/s² = 1.7210368 N·m |
| Gravity | 9.81 m/s² = 35.036 stud/s² |

**Per physics step** (`RunService.PreSimulation`, in `VehicleController`):

1. Read input and rigid-body state, and convert to SI.
2. **Aero:** drag at the center of mass, and downforce at each axle (proportional to v²).
3. **Suspension:** each wheel casts a tire-sized sphere downwards, so it rolls over curbs and road edges instead of hitting them as steps. Spring, digressive damper and anti-roll bar give the tire's normal load, so weight transfer and downforce reach the tires physically.
4. Contact-patch velocity in each wheel's frame.
5. **Torques:** engine torque curve with a progressive pedal map and rev limiter → 8-speed gearbox (engine inertia reflected through the ratio) → limited-slip differential. Brake torque per wheel uses the brake bias and optional ABS; traction control is optional.
6. **Wheel spin:** each wheel's angular speed is integrated in 4 semi-implicit substeps per frame, with friction torques that can stop a wheel but never reverse it (real lockup). An overshoot guard keeps the flat post-peak region of the tire curve stable.
7. **Tire forces** (simplified magic-formula, combined slip): grip rises to a peak, then falls off progressively. Force follows the slip vector, so wheelspin or lockup trades away cornering grip. These forces are applied with `VectorForce` at each contact point.
8. Telemetry and the debug HUD.

Chassis velocity and CFrame are **never set directly**. The Roblox physics engine integrates the forces.

**Car:** 798 kg, 45/55 front/rear weight, center of mass 0.30 m high, 3.6 m wheelbase, about 700 kW peak, aero balance about 40% front.

## Controls

| Key | Action |
|---|---|
| W | Throttle (ramps in over 0.67 s) |
| S / Shift+S | Brake at 28% pedal / 100% pedal |
| A / D | Steer (slower at high speed on keyboard) |
| E / Q | Shift up / down (switches to manual) |
| G | Toggle automatic shifting |
| V / B | Toggle traction control (on by default) / ABS (off by default) |
| T | Toggle the physics debug panel |
| C | Chase / cockpit camera |
| R | Reset to the paddock |

## Multiplayer and authority model

- The driver's client gets **network ownership** of its car, so physics runs locally with no input lag.
- The server owns spawn slots, seating, and resets (owner-only and rate-limited). The reset position is always chosen by the server.
- Clients never submit positions, results or currency. Because the owner simulates its own car, anything competitive (lap times, rewards) must be validated on the server in future work.

## Testing

`Dev/TestDriver.luau` drives the car with exact analog inputs, through a Studio-only input override, and records telemetry each physics step. It includes a lookahead-steering driver that laps the handling loop. Latest automated results, run in Studio:

| Test | Result |
|---|---|
| Full lap of the handling loop | Completed, max sideslip 3.7°, 0 wheel-contact losses in 3,671 steps |
| Straight-line full throttle | Heading change 0.00° |
| 0.3 s steering tap at 220 km/h, throttle held | Sideslip 0.9°, rear tires at 84% of grip |
| Full lock at 270–280 km/h, throttle held | 3.1 g, pushes wide (understeer) instead of spinning |
| 50% throttle in a 1 g corner | Sideslip 0.9° |
| Full throttle in a corner, 0.25 s driver reaction, TC on | Sideslip peaks at 10.7°, recovers 0.27 s after lifting |
| 28% braking in a corner | Keeps turning, no lockup (front slip ratio −0.09) |
| 100% brake from 254 km/h, ABS off | 3.4 g, straight, stops in 107 m |

## Known limitations

- **Parallel steering:** both front wheels turn by the same angle; Ackermann geometry is not modeled yet.
- **Plausible estimates, not real data:** the tire, engine and aero parameters are tuned estimates, not data from any real car or tire.
- **60 Hz force updates:** forces are recalculated once per frame and held across Roblox's internal 240 Hz substeps. Suspension rates (about 3.3 Hz ride frequency) are chosen to stay stable under that limit.
- **Keyboard only:** with TC off, full throttle mid-corner in gears 1–3 spins the car, as it would in a real car of this power. Analog (gamepad) input is not implemented yet.
